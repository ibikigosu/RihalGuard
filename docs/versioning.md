# RihalGuard versioning

RihalGuard uses Semantic Versioning for the contract standard and schema.
The `standard_version` field identifies the RihalGuard contract version, while the top-level `version` identifies the individual agent contract.

## Compatibility

- Patch releases clarify documentation or validation without changing valid contract meaning.
- Minor releases may add optional backward-compatible fields and guidance.
- Major releases may add required fields, remove fields, rename fields, or change field meaning.
- A contract pins one exact `standard_version`.
- A schema URL for a published schema version is permanent and remains available for contracts pinned to it.

The current `rihalguard-v1.schema.json` accepts `standard_version` `1.0.0` exactly.
A future minor or major release must publish a new schema file rather than silently changing the version expected by an existing schema URL.

RihalGuard v1 retains `workflow_pattern`, string-based `human_review.required_when`, and `output_policy.never_fabricates` for compatibility.
The v1 schema permits `human_review.trigger_definitions` and `output_policy.unsupported_claim_policy` for clearer semantics, and reference blueprints in this repository require them.
Removing the legacy fields requires a future major version and migration guidance.

## Migration rules

Breaking changes require:

1. a new major schema file
2. migration notes describing old and new field mappings
3. an automated or deterministic migration path where practical
4. a validation warning period before an old major becomes unsupported
5. explicit runtime-adapter compatibility notes

Support windows are set by the Rihal standard owners when a new major version is approved.
This repository must not invent a retirement date without that decision.

`CHANGELOG.md` is generated by the release process and must not be edited manually.
